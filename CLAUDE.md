# Mind For Apps — Project Guide

Marketing site + admin CMS for a no-code/MVP development agency. Content (case studies, solutions, services, templates) is editable through a password-protected admin panel, backed by Supabase. Repo: [Mind-For-Apps/mindforapps](https://github.com/Mind-For-Apps/mindforapps), deployed on Vercel (auto-deploys on push to `main`).

## Stack

- **Next.js 16** (App Router, Turbopack) — see `AGENTS.md`; this version has breaking changes vs. training data (e.g. `proxy.ts` replaces `middleware.ts`). Check `node_modules/next/dist/docs/` before assuming an API.
- **Tailwind CSS v4** — tokens live in `@theme` blocks inside `src/app/globals.css`, not `tailwind.config.js`.
- **Supabase** — Postgres (schema in `supabase/migrations/`), Auth (admin login), Storage (all content images, in the `case-study-media` bucket despite the name — it holds case study, solution, template, and reference-data images too). Project ref `rvsgqzidyzgohmokogfu`.

## Important decisions (and why)

- **Images upload straight to Supabase Storage**, not pasted URLs — user explicitly chose this over a simpler "paste a link" admin field, for a cleaner long-term workflow. All seed scripts re-upload Bubble CDN images to Storage rather than linking the original Bubble URLs.
- **Services / Tools / Team Involvement / Categories are separate lookup tables** with their own mini-admin CRUD (`/admin/reference`), linked to case studies / solutions / templates via junction tables — not inline text — because the source data (Bubble) reused the same small set of values across many records.
- **Key Features Delivered and "What Was Built" are both per-case-study child tables** (`case_study_key_features`, `case_study_web_architecture`) — not shared lookups — each row only appears under one case study in the source data. `web_architecture` started life as a plain `text[]` column (see below) but was migrated to a child table in `0008` once real per-item icons became available, mirroring `case_study_key_features`. **Solution Feature Categories/Labels** follow the same "child of one parent" pattern for solutions (currently only seeded for the `real-estate` solution — see Known gaps).
- Bubble fields typed "List of texts" (Client Goal, The challenge was, Suitable For, Project-based collaboration, Web Architecture, Designed For, With/Without MFA, etc.) became plain `text[]` columns — no separate tables, since they're never reused across records.
- **Homepage sections read live from Supabase** (Server Components, no caching layer) rather than staying hardcoded — user wanted the admin panel to have immediate visible effect.
- **Single admin user**, created manually via Supabase Dashboard → Authentication → Users — no signup flow was built, since only one person needs access.
- Stat-highlight text fields (`text_1`…`text_6` on case studies) are stored **raw**, including their `[b][size=4][color=...]` Bubble-style pseudo-markup. `parse-highlight.ts` parses and renders this for case studies' "Outcome & Impact" section (colors are rendered exactly as stored per-record via inline `style`, not mapped to a Tailwind token). Solutions' `text_0`–`text_8` are plain copy fields (no pseudo-markup) — they're now all mapped to specific sections of `/solutions/[slug]` (see `getSolutionBySlug()` in `src/lib/solutions.ts` for the exact field→section mapping) rather than being generic/interchangeable.
- **The case-study detail page's decorative illustrations have no per-case-study meaning** — they're the same 5 static images for every case study (Challenge/Collaboration/Client Goal/Solution/Team-Involvement sections), not derived from case data. Don't try to make them contextual to the content; they're pure Figma decoration.
- **"Key Features Delivered" and "What Was Built" are two different sections** on the detail page and must not be conflated, even though both are now `label` + `icon_url` child tables with an identical shape (`case_study_key_features` / `case_study_web_architecture` respectively) — they're separate tables because they're separate Bubble source fields with independent data.
- **The case-study detail page's true section order/design was confirmed from a full saved copy of the live reference page** (user-provided HTML export in `Assets/`, gitignored) rather than only the screenshots initially shared: the real order is Outcome & Impact → client testimonial (dark navy card) → **Team Involvement** (the `team_involvement_types` lookup, previously undiscovered as a detail-page section) → Suitable For (bordered pill grid, heading has a trailing colon). Initial screenshots hadn't covered the testimonial/Suitable For styling or Team Involvement at all — if another rich field turns out to be unrendered, check for a saved reference page in `Assets/` before guessing.
- **Templates' `new_images` field** turned out to reference a separate Bubble "New Images" type that was just a plain image wrapper (image + unused alt text) — rather than modeling it as its own Supabase table, the field was resolved directly into a `text[]` of real image URLs during seeding (see migration `0007`).
- **The Footer's "Start Your Project" form writes to Supabase directly** (`project_inquiries` table + `project-inquiry-files` bucket), not to an external email/CRM/webhook — user explicitly chose "don't lose the data even without a notification pipeline yet" over standing up a third-party integration. Submissions are only visible via `/admin/inquiries`; there's no email alert when one comes in.
- **`project-inquiry-files` is a private Storage bucket** (`public: false`), unlike `case-study-media` — inquiry attachments can be client briefs/NDAs, so RLS only allows public *insert* (anyone can attach a file when submitting) and restricts *read* to the authenticated admin. This means `file_paths` on `project_inquiries` stores raw Storage paths, not public URLs — the admin inquiries page resolves them to temporary signed URLs on render via `createSignedUrls()`.
- **Category filtering on Templates is real, client-side filtering** (not a fake/decorative UI) — `TemplatesBrowser.tsx` holds `templates` + `categories` in one client component and filters in-memory by `category_id` membership.
- **Add-ons section is static/hardcoded content** (not DB-driven) — the 4 blocks (Template Customization, Plugins Development, QA & Audit, Ongoing Support) live directly in `AddOns.tsx`, rebuilt to match the Figma frame (node `155:219`) including real per-card graphics exported from Figma (`public/images/addons/`) and real body copy. All 4 still link to `href="#"` (destinations not yet provided).
- **Card layout breakpoints intentionally don't match Figma's implicit desktop-only sizing**: each card's column→row switch is deferred to `lg:` (1024px, not `sm:`) and the minor-cards grid goes 1→2→3 columns at `md:`/`xl:` (not straight to 3 at `sm:`) — copying Figma's fixed pixel widths onto an `sm:` breakpoint caused a fixed-width image to sit next to text with no room left on real tablet widths, and flex's default `min-width: auto` let the text overflow past the card edge instead of wrapping. Any new fixed-size-image-next-to-text card should follow this pattern: `min-w-0` on the text sibling, and don't let a "go wider" breakpoint (row layout, more grid columns) land at the same breakpoint as another one — see `AddOns.tsx`.
- **The solution detail page mixes DB-driven and static/hardcoded sections deliberately** — Hero, comparison lists, Feature Categories, Build-track pricing, and "What's Included" are genuinely per-solution data; Process steps, the results/stats block, FAQ, and Grow-track pricing are static because their copy is ~identical across every solution in the reference screenshots (Process just interpolates the solution's `title` into one sentence). Don't assume everything on that page needs a DB field — check `CHANGELOG.md`'s entry for exactly which sections are which before "fixing" a static one.
- **Testimonials are a single shared pool**, not per-case-study or per-solution — the reference quotes read as generic agency testimonials (about MindForApps' service, not about any one industry), so one small `testimonials` table is reused identically wherever testimonials are shown (the solution detail page's `TestimonialsCarousel` and the homepage's `Testimonials`/`TestimonialsSlider`, each with its own visual treatment), rather than duplicating rows per solution. The homepage version's per-testimonial "project showcase" (screenshot + client logo, from the Figma frame) is backed by two real optional columns (`project_image_url`/`project_logo_url`, migration `0012`, editable per-testimonial in `/admin/testimonials`) rather than the Figma placeholder ("Dewie") assets — the block only renders when a testimonial actually has one of those set, falling back to just the plain `company` tagline line otherwise. All 5 real testimonials now have both fields populated from a fuller Bubble CSV export (`npm run seed:testimonials`, re-run after the user supplied `Logo`/`Project image` columns that weren't in the original import).
- **The homepage "Why Us" section (`WhyUs.tsx`) is static/hardcoded content**, same pattern as `AddOns` — the Before/After pain-point and outcome lists are literal Figma copy, not DB-driven. The "After" list has a verbatim duplicate line ("Fully customized design and logic" appears twice) because that's how it exists in the source Figma file — not a bug introduced during implementation, but worth flagging to the client.
- **The solution detail page's "What's Included" section is a responsive card grid, not the hand-positioned mind-map diagram** shown in the Figma/reference screenshots (dotted connector lines from a central "Solution" node to scattered feature bubbles) — a fixed-position diagram doesn't adapt to a variable item count per solution or to mobile widths, so the same data (icon/title/subtitle/tags) is rendered as a grid instead.

## Coding rules observed in this repo

- Server Components by default; `"use client"` only where real interactivity is needed (repeaters, image upload, mobile nav, sliders/carousels, drag-to-scroll, category filtering, login form).
- Admin mutations are Server Actions (`"use server"` files), bound with `.bind(null, id)` for update/delete rather than hidden form fields.
- Shared UI is extracted aggressively to avoid duplication — e.g. `CaseStudyCard` is used by both the homepage slider and `/case-studies`; `TextField`/`TextAreaField`/`SelectField`/`FormSection` are shared across every admin form; every admin list page (Case Studies, Solutions, Templates) shows a thumbnail preview using the same inline pattern (image or a gray placeholder div).
- No comments unless explaining a non-obvious constraint (see the "Gotchas" section below for examples of what actually warranted one).
- Images always go through `next/image`; remote patterns for the Supabase Storage domain are configured in `next.config.ts`.
- After any change, run `npm run build` to catch type/lint errors before calling something done — this project has caught several real bugs this way (e.g. Tailwind `@theme` circular reference, JSX escaped-quote parse error).
- **Any script that splits a Bubble "list of X" export field must split on `" , "` (space-comma-space), never bare `","`** — see Gotchas below. This bit us once already (see Known gaps / history) and every seed script's `splitList` helper now does this correctly.

## Git workflow

- Collaborator access on `Mind-For-Apps/mindforapps` (not a personal fork) — `origin` points straight at the org repo, confirmed `push: true`.
- **This is specifically how this user contributes** — not a team-wide policy being imposed on other developers, who keep working however they already do. When making changes for this user: branch → push → open a PR, and **never merge it** — someone else on the team reviews and merges. This is the opposite of solo-repo projects where the same agent both opens and merges; don't carry that habit over here.

## Gotchas learned the hard way

- **Figma's `fill="var(--fill-0, black)"` SVG export pattern only works if the SVG is inlined into the DOM** (e.g. as JSX or via `dangerouslySetInnerHTML`) — it does nothing when the file is loaded through `next/image`/`<img src="...">`, which is how every icon/logo in this codebase is used. Setting the CSS custom property on a parent element (even via a Tailwind arbitrary property like `[--fill-0:white]`) has zero effect, because an `<img>`-loaded SVG renders in its own isolated context that doesn't inherit the host page's CSS. To get a differently-colored version of an existing logo/icon SVG (e.g. white-on-dark), make an actual separate file with the color hardcoded (see `public/images/logo-white.svg`) — don't try to theme it via CSS variables from outside.
- **`next/image` silently refuses remote `.svg` files unless `images.dangerouslyAllowSVG: true` is set in `next.config.ts`.** This project uses SVG icons throughout (Tools, Key Features Delivered, Web Architecture/"What Was Built") re-uploaded to Supabase Storage — without this flag, `/_next/image?...` returns a 400 ("image type is not allowed") for every one of them, and the `<img>` just never loads (no visible error in the UI, easy to miss). Fixed once discovered, paired with the recommended `contentDispositionType: "attachment"` + a locked-down `contentSecurityPolicy` (Next's own mitigation for serving SVG, which can contain scripts). If a newly-added icon/image silently doesn't render, check this before assuming the data is wrong.
- **Bubble CSV list-export separator is `" , "` (space-comma-space), not `","`.** List items can themselves contain commas (e.g. "Predictable, fixed pricing" is one item, not two), so a naive `.split(",")` silently corrupts data — it did, in production, across several `text[]` columns (Client Goal, The challenge was, WEB architecture, Suitable For, Project-based collaboration on case studies; `whats_included` on services) before this was caught and fixed by re-running the seed scripts with the corrected splitter. Every current seed script's `splitList()` helper handles this correctly; keep doing it that way in any new one.
- **Supabase Storage keys must be ASCII-safe.** A source slug can contain a look-alike non-Latin character (e.g. a Cyrillic "с" instead of Latin "c" — happened with one real template slug) that Storage rejects as an "Invalid key" on upload. Seed scripts that build Storage paths from a slug should sanitize the *path* separately (see `storageSafe()` in `scripts/seed-templates.ts`) even if the DB `slug` column is left as-is (or fix the slug too, if it's clearly a typo).
- **Re-running a seed script must never duplicate rows.** Early versions of `seed-services-and-features.ts` used a blind `.insert()` for the `services` table; re-running it after an unrelated data fix created 4 duplicate rows (caught and cleaned up manually). Every lookup-table seed now checks for an existing row by name/title first and updates it instead of blindly inserting.
- **Tailwind v4 `scale`**: uses the native CSS `scale` property, not `transform`. `-scale-x-100` works fine as a class, but verify via `getComputedStyle(el).scale`, not `.transform` (the latter stays `"none"`).
- **`@theme` vs `@theme inline`**: only use `inline` for referencing runtime-generated CSS vars (e.g. `next/font` variables). Plain color tokens belong in a normal `@theme { }` block. Putting them in `@theme inline` with a self-referencing `var(--x: var(--x))` creates a circular reference that silently breaks — the computed value becomes invalid/`none` with no error.
- **Next.js 16 proxy**: `middleware.ts` is deprecated; the file is now `proxy.ts`, exporting `proxy()` (or default export) + optional `config.matcher`.
- **CSS `scroll-snap-type: mandatory` fights direct/programmatic `scrollLeft` writes** that don't originate from a real scroll gesture — a plain `el.scrollLeft = X` assignment (or even `scrollBy`) can get silently reverted to the nearest snap point. The homepage carousels (`SolutionsCarousel`, `ServicesSlider`, `TemplatesBrowser`) work around this by animating scroll manually via `requestAnimationFrame` and writing `scrollLeft` every frame, rather than relying on the browser's native smooth-scroll behavior for timer-driven autoplay.
- Figma-exported SVG assets can have mismatched geometry vs. their fill color (arrow-left/arrow-right were identical paths, different colors — the "right" arrow pointed left). Verify visually before trusting an asset's orientation.
- **Preview browser tooling in this environment is frequently flaky, independent of app code**: the screenshot action can time out repeatedly (sometimes recovers after opening a fresh tab or a `wait`, sometimes needs several retries — this happened repeatedly across sessions and is not a signal that the page is broken). Separately, this sandbox does not appear to continuously repaint/commit DOM changes that originate from a `setInterval`/`requestAnimationFrame` timer without an explicit tool-driven interaction (click, screenshot) forcing a render — so autoplay-style features may not visibly animate under `javascript_exec` + `wait` polling even though the code and a real click both work correctly. Verify timer-driven behavior by code review + a real click/drag test, not by passively polling `scrollLeft` after a `wait`.
- **Editing the same client component file many times in one dev session can leave its event handlers silently non-functional** (button clicks stop firing) even though the code is correct — this is Turbopack/Fast-Refresh state going stale, not a bug. Fix: `preview_stop` + `preview_start` (full dev server restart) before trusting a "click does nothing" result, especially after several rapid edits to one file.
- **Next's dev image optimizer (`/_next/image?url=...`) can cache a blank/broken response against a URL indefinitely, surviving both a `.next/cache/images` deletion and a full dev-server restart** — if you request a Figma-sourced local image before the file on disk is actually correct (e.g. mid-debugging, wrong asset downloaded), the optimizer route appears to key its cache/ETag by URL+params rather than file content hash, so fixing the file afterward doesn't invalidate it (`304 Not Modified` keeps winning). Symptom: the `<img>` renders with plausible-looking (proportionally correct) but wrong `naturalWidth`/`naturalHeight`, and paints nothing visible, while a manual `fetch(url, {cache:'no-store'})` on the exact same URL correctly returns the fixed bytes. Fix: rename the file (and update the reference) to a URL that was never requested before — don't waste time on `.next/cache` clearing or server restarts, they don't help. Happened once with `why-us/wave-bg.png` → renamed to `wave-bg-illustration.png`.
- **A Figma node can have multiple candidate raw-image assets for the same visual element, and `get_design_context`'s inlined asset URL isn't always the right one.** For a background illustration on the "Why Us" section, the URL `get_design_context` generated in its reference code pointed at a blank/empty asset, while the correct full-resolution image was sitting in `download_assets`' `rawImages` list for the same node under a different URL. If a downloaded decorative image renders blank, cross-check `download_assets` before assuming the source file itself is broken.
- `create-next-app` refuses project names with capital letters — this is why the app was scaffolded into a temp lowercase subfolder and moved up, rather than directly into `D:\MFAsite`.

## Admin panel

- URL: `/admin` (redirects to `/admin/case-studies`), gated by Supabase Auth via `src/proxy.ts`.
- Admin users are created manually in the Supabase Dashboard → Authentication → Users (no signup flow exists on purpose).
- Nav: Case Studies, Solutions, Templates, Reference Data, Testimonials, FAQs, Inquiries, plus "View site" / a clickable "MFA Admin" logo to get back to `/`.
- CRUD: Case Studies, Solutions (incl. nested Feature Categories/Labels and What's-Included repeaters, plus Build-track pricing fields), Templates (incl. Category/Feature-tag checkboxes and Platform-type/User-roles selects), Reference Data (Services / Tools / Team Involvement / **Categories** — all shared lookup tables), Testimonials and FAQs (both simple shared pools, full CRUD).
- **Inquiries** (`/admin/inquiries`) is read-focused, not full CRUD — no create/edit form, since rows only ever come from the public Footer form. Just mark read/unread and delete.
- All admin list pages (Case Studies, Solutions, Templates) show a 40×40 thumbnail per row (main/first image, or a gray placeholder if none).
- Images upload directly to the `case-study-media` Storage bucket from the admin forms.

## Database

- Schema, in order: `supabase/migrations/0001_case_studies_and_solutions.sql` (base: case_studies, solutions, services, tools, team_involvement_types + junctions + Storage bucket), `0002_extend_services.sql` (services description/picture/tags), `0003_extend_solutions.sql` (solutions rich fields + `solution_tools`), `0004_solution_features.sql` (`solution_feature_categories` + `solution_feature_labels`), `0005_categories.sql` (`categories` lookup), `0006_templates.sql` (`templates` + `template_categories` + `template_feature_tags` + `template_features`), `0007_resolve_template_new_images.sql` (renamed a column), `0008_case_study_web_architecture.sql` (adds `case_study_web_architecture` child table, drops the old `web_architecture text[]` column — must be followed by `npm run seed:web-architecture`, see below), `0009_project_inquiries.sql` (`project_inquiries` table + private `project-inquiry-files` Storage bucket for the Footer contact form), `0010_solution_detail_page.sql` (`solution_included_features` child table, `build_price_low`/`build_price_high`/`build_checklist` columns on `solutions`, and a shared `testimonials` table — all for `/solutions/[slug]`), `0011_faqs.sql` (a shared `faqs` table feeding `/faq`, the homepage, and the Real Estate solution page), `0012_testimonial_project_showcase.sql` (adds optional `project_image_url`/`project_logo_url` columns to `testimonials`, for the homepage Testimonials card's project-screenshot-and-logo block). These must be run manually in the Supabase SQL Editor — this environment only has the anon key, not a DB connection string or the ability to run DDL via the JS client.

- Env vars: `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY` live in `.env.local` (gitignored) and must also be set in Vercel's env vars for prod. `SUPABASE_SERVICE_ROLE_KEY` is only ever added temporarily for running a seed script, then removed — never used by the app itself, never committed.

## Data seed scripts (`scripts/`)

One-off migrations of the client's real content from their old Bubble.io app. Require `SUPABASE_SERVICE_ROLE_KEY` temporarily in `.env.local` — never commit it, remove it again after running. Every script upserts by a natural key (slug/title/name), so re-running any of them is safe:

- `npm run seed:case-studies` — imports the 6 real case studies and re-uploads their images to Storage.
- `npm run seed:services-features` — seeds the Services lookup table (with description/picture/tags) and per-case-study Key Features, and links both to case studies.
- `npm run seed:tools` — uploads icons for the Tools lookup table (16 tools).
- `npm run seed:solutions` — imports the 5 industry solutions (Real Estate, EdTech, HealthTech, Service Booking, Marketplace), re-uploading images and linking tools.
- `npm run seed:solution-features` — imports the Feature Categories/Labels for the `real-estate` solution only (the only one with source data so far).
- `npm run seed:categories` — seeds the 8 Categories used to filter Templates.
- `npm run seed:templates` — imports the 47 templates (36 marked public), re-uploads `images`/`design_images`/`new_images`, and links Categories + Feature tags.
- `npm run seed:web-architecture` — populates `case_study_web_architecture` ("What Was Built" items with real icons) for the 6 case studies from `scripts/web-architecture-data.json`. Must run after migration `0008`.
- `npm run seed:testimonials` — populates the shared `testimonials` table (5 real client quotes + photos) from `scripts/testimonials-data.json`. Must run after migration `0010`.
- `npm run seed:faqs` — populates the shared `faqs` table (37 real Q&As, incl. homepage/Real-Estate flags) from `scripts/faqs-data.json`. Must run after migration `0011`.
